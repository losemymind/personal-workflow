# 技能创建器（skill-creator）

## 概述

本技能指导如何从零创建、改进、验证并安装个人工作流技能。技能的本质是一组可复用的指令与资源（`SKILL.md` 及其目录），为 LLM 客户端提供精确的触发条件与操作流程。本技能的目标是产出**可被可靠触发、执行结果可预期、可跨客户端复用**的高质量技能，并按个人工作流（PersonalWorkflow）的规范归档到 `skills/` 目录。

## 何时使用此技能

- 用户要求「把这个工作流做成一个技能」、「创建一个 skill」
- 需要改进或重构一个现有技能
- 需要评估一个技能是否会被 LLM 可靠触发、指令是否清晰、结构是否达标
- 需要把一个新技能安装到 claude / opencode / codex / deepseek 等客户端的 skills 目录
- 项目中反复出现某类手动流程，值得沉淀为技能

## 工作原理

核心循环：**捕捉意图 → 设计 → 编写 → 测试 → 改进 → 安装/归档**。

### 阶段 1：捕捉意图

动手写文件之前，先明确需求。优先从当前对话中提取信息（用户提到的工具、步骤顺序、纠正过的错误、输入输出格式），补足缺失信息：

1. 这个技能要让 LLM 能做什么？
2. 什么时候应该触发？哪些用户表述 / 上下文等于触发条件？
3. 预期的输出格式是什么？
4. 是否需要设置测试用例验证？可客观验证的技能（文件转换、数据抽取、代码生成、固定流程）适合写断言；主观类技能（写作风格、创意）以用户定性评审为主。

需求不明确时逐条提问，得到确认后再进入下一阶段。

### 阶段 2：研究与设计

- 若技能涉及专业领域，先查可用文档 / 类似技能 / 最佳实践，带着上下文去设计，减少用户负担。
- 参考现有技能的风格与结构（见 `skill-anatomy` 规范），从简单开始，尽量先做到「最小可行」，再按反馈扩展。
- 确定技能目录结构与必要资源（脚本、参考文档、示例、模板）。

### 阶段 3：编写 SKILL.md

按「技能目录解剖」与「内容结构」两节的要求编写。要点：

- `name` 用小写-连字符，与目录名完全一致；是技能的稳定标识，后续改进时保持不变。
- `description` 是触发的主要机制：同时包含「技能做什么」+「何时触发」+ 具体触发场景。实测表明 LLM 倾向**欠触发**技能，描述可稍「主动」：直接列举会触发它的用户说法，即使没有字面提到技能名。
- 正文用祈使句、动作动词、具体步骤；解释每个指令的**为什么**，避免用一串大写的 MUST/NEVER 堆砌。
- 有可复现任务的技能应附带 `scripts/` 脚本，避免每次调用重复造轮子。
- 示例放在正文代码块中，或引用 `examples/` 目录。

### 阶段 4：测试与迭代

创建初稿后，提出 2-3 个真实用户会说的测试提示词，与用户确认后运行：

- **有技能** 和 **无技能（基线）** 两组对比运行同一提示词，记录输出、耗时与 token。
- 针对可客观验证的断言打分（存在性、包含子串、格式正确、命令执行成功等）；主观部分交给用户看结果做定性评审。
- 把结果整理成便于用户对照的形式（输出对比 + 量化指标），请用户逐条反馈。
- 根据反馈改进：从反馈中**归纳共性**而不是死板套用；剔除不生效的指令；把各测试中都重复手写的辅助脚本沉淀为 `scripts/`。
- 重复「改进 → 重跑 → 评审」直到用户满意或反馈为空。

### 阶段 5：描述优化（触发测试）

技能完成后，优化 `description` 的触发准确性：

1. 生成约 20 条真实风格的触发查询：一半应触发、一半不应触发（近似的干扰项最有价值——关键词重叠但实际需要别的东西）。
2. 请用户审阅并签名确认查询集。
3. 用两种描述（现版 vs 改进版）各自跑查询，对比触发率，选择测试集分数更高的版本。
4. 向用户展示前后对比与得分。

### 阶段 6：安装与归档

- 按「多客户端安装指引」把技能复制到目标客户端的 skills 目录。
- 验证安装：重启客户端后，用该技能处理一个真实小任务确认可用。
- 经验证、可复用的技能提交到 PersonalWorkflow 仓库的 `skills/<name>/`，遵循质量检查清单与安全护栏。

## 技能目录解剖（Anatomy）

```
skills/
└── <skill-name>/
    ├── SKILL.md              ← 必需：主技能定义（frontmatter + 指令）
    ├── examples/             ← 可选：示例文件
    ├── scripts/              ← 可选：辅助脚本
    ├── templates/            ← 可选：输出模板
    ├── references/           ← 可选：参考文档（超过约 300 行的文档应附目录；多领域用子文件按需加载）
    └── README.md             ← 可选：附加说明
```

关键规则：**只有 `SKILL.md` 是必需的**。正文保持在 500 行以内；超过时把细节下沉到 `references/`，并在正文给出明确的读取指引。技能须满足「无意外原则」：不能包含恶意内容，也不能在意图上隐藏改动。

## 前置元数据字段规范

SKILL.md 顶部用 `---` 包裹 YAML frontmatter：

```yaml
---
name: <skill-name>                 # 必需：小写-连字符，与目录名完全一致
description: "..."                 # 必需：一句话说明（含触发场景），≤200 字符
category: <category>               # 必需：见下方分类
risk: <none|safe|critical|offensive|unknown>  # 必需
source: <self|community|official|URL>         # source: self 表示原创
date_added: "YYYY-MM-DD"           # 必需
author: <your-name-or-handle>      # 可选
tags: [tag-one, tag-two]           # 可选：小写、≤5 个
tools: [claude, opencode, codex]   # 可选：支持的客户端
---
```

**风险级别：**
- `none` — 纯文本 / 推理，无命令或状态变更
- `safe` — 读取文件、运行非破坏性命令（推荐用于多数指导类技能）
- `critical` — 修改状态、删除文件、推送生产环境
- `offensive` — 渗透测试 / 红队；**必须**含「仅限授权使用」警告，并强制要求执行前向用户确认
- `unknown` — 遗留 / 未分类；**新技能不要用**

**分类常用值：** `development` / `frontend` / `backend` / `testing` / `devops` / `architecture` / `security` / `ai` / `prompt-engineering` / `git` / `productivity` / `documentation` / `planning` / `communication` / `research` 等。

## 内容结构与写作指南

推荐结构（必需章节：概述 / 何时使用 / 工作原理；其余可选）：

```markdown
# <技能标题>
## 概述        # 2-4 句：做什么、为什么存在
## 何时使用此技能   # 具体场景列表（触发条件）
## 工作原理     # 步骤化执行流程（技能核心）
## 示例        # 至少 1 个可立即复制的代码块/交互示例
## 最佳实践     # ✅ 要这样做 / ❌ 避免什么
## 相关技能     # @other-skill 引用
## 常见问题     # 故障排查
## 限制和注意事项  # 已知边界与做不到的事
## 安全与安全说明  # 涉及命令/安装/权限时才需要
```

**写作要点：**

- 用清晰直接的动作动词：「创建文件…」「在继续之前检查…」，避免「应该被创建」「您可能想要考虑」。
- 示例要具体、可直接使用；标注输入/输出。
- 定义输出格式时直接给出固定模板：
```markdown
## 报告结构
ALWAYS 使用此模板：
# 标题
## 执行摘要
## 关键发现
## 建议
```
- 使用「渐进式披露」：`## 基本用法` 留给常见场景，`## 高级用法` 留给复杂场景。
- `description` 里说明「何时用」，正文里写「怎么用」——不要互相对调。

## 质量检查清单

提交/入库前逐项核对：

**元数据：**
- [ ] frontmatter 是有效 YAML，`name` 小写-连字符且与目录一致
- [ ] `description` ≤200 字符，包含做什么 + 何时触发
- [ ] `risk` / `category` / `source` 已声明

**内容质量：**
- [ ] 指令清晰、可操作（祈使句、动作动词）
- [ ] 有明确的「何时使用」触发说明
- [ ] 至少有 1 个可复制粘贴的示例
- [ ] 列出了限制和注意事项（已知边缘情况 / 做不到的事）
- [ ] 技术准确性已验证，无拼写错误

**可用性：**
- [ ] 初学者能按步骤执行
- [ ] 解决一个真实问题，而非空泛建议
- [ ] 不依赖超窄的具体例证（避免过拟合到测试用例）
- [ ] 涉及命令/安装的内容通过安全审查（无 `curl ... | bash` 等管道，无明文密钥示例）

## 安全护栏

- 攻击性技能（渗透 / 红队 / 利用）：**必须以「AUTHORIZED USE ONLY / 仅限授权使用」免责声明开头**，指令中明确要求代理在执行任何利用或攻击命令前请求用户确认，推荐在 Docker/VM 等受控环境运行。
- 防御性/分析类技能：审计默认只读；未经用户明确同意不得把数据上传到第三方。
- 技能正文中的命令示例不得包含危险管道（`curl|bash`、`wget|sh`、`irm|iex`）或内联密钥/token；确为操作必需的，需使用 `<!-- security-allowlist: ... -->` 声明并附警告上下文。
- 不编写、不复制恶意软件、勒索软件或非教育性利用负载。

## 多客户端安装指引

技能本体是通用目录格式 `skills/<name>/SKILL.md`，安装方式因客户端而异。复制目录后需**重启客户端**才会生效。

- **Claude Code**：`~/.claude/skills/<name>/`（用户级）；项目级放 `.claude/skills/<name>/`。仓库 `~/.claude/skills` 中结构为 `<name>/SKILL.md`。技能会在触发时被加载，触发依据是 `description`。
- **OpenCode**：用户级 `~/.config/opencode/skills/<name>/SKILL.md`；项目级 `.opencode/skills/<name>/SKILL.md`；也可在 `opencode.json` 的 `skills.paths` 注册任意目录（loader 递归扫描 `**/SKILL.md`）。
- **Codex（OpenAI）**：`~/.codex/skills/<name>/SKILL.md`（复制 `skill-creator/` 目录到 `~/.codex/skills/` 后重启 Codex，再通过 `/skills` 或提及 `$skill-creator` 触发）。
- **DeepSeek Harness**：技能目录路径以当前版本官方文档为准（用户级通常位于该工具 config 目录下的 `skills/`，项目级约定视版本而定）；安装后重启并验证触发。

安装后验证：用一个真实的小任务触发试运行，确认技能被正确加载、按指令执行。

## 常见问题

**Q: 技能不会被触发怎么办？**
A: 优化 `description`：加具体触发场景、改用用户可能用的口语/近义说法，可补充近干扰项做触发测试（见阶段 5）。

**Q: 技能太长超过 500 行？**
A: 把细节拆到 `references/` 子文件并按需加载，正文保留工作流与选择逻辑，给出读取指引。

**Q: 技能同时覆盖多个领域？**
A: 按变体拆分：正文放工作流+选择逻辑，`references/` 下每领域一个文件（如 `aws.md` / `gcp.md` / `azure.md`）。

**Q: 一个工作流应该做成技能还是 Agent 或命令？**
A: 简短的单次交互用命令；可复用的多步骤流程先做技能；技能稳定、需要持续关注某领域后再考虑专职 Agent。

## 限制和注意事项

- 本技能产出的是**通用目录格式**的技能，各客户端可能对 frontmatter 的扩展字段支持程度不同；以目标客户端文档为准。
- 触发准确性无法 100% 保证，`description` 需要持续迭代。
- 本技能不自动执行测试运行环境（如无 Python 的环境）、不代替用户最终审核；安装到生产客户端前应先在测试项目验证。
- Windows 环境下安装路径与类 Unix 环境不同（如 `~/.config` 对应 `%USERPROFILE%\.config`），跨平台使用请以实际路径为准。
